# Стриминг чанков и бесконечный мир — технический план

Статус: **проектирование**. Код не написан, сборка не проверена (на машине нет компилятора).
Цель: убрать фиксированный мир 864×864 и перейти к подгрузке чанков вокруг игроков.

---

## 0. Честная оценка

Это не патч и не «переписать один файл». Это замена трёх подсистем:

1. **Хранилище чанков** (`ServerChunkCache` + `ChunkStorage` + формат сейва).
2. **Рендер** (`LevelRenderer` индексирует чанки абсолютными координатами в статических массивах).
3. **Генерация и границы** (`LevelData::m_xzSize`, структуры, спавн, ад, Энд).

Объём: ориентировочно 3–5 тыс. строк изменений в 20+ файлах.
Срок для человека, знающего код: 6–12 месяцев full-time. Для сравнения: 4J переходила
с 864 на 5120 больше года и это был не бесконечный мир, а просто больший.

**Важно:** после стриминга память перестаёт быть стеной. 300–500 чанков в окне — это 10–15 МБ.
Стеной становятся процессор (генерация и свет), диск (Xbox 360 HDD) и, главное, рендер.
То есть «бесконечный мир на 360» — не физически невозможно, а очень дорого по инженерии.

Ключевой момент: индексация идёт **абсолютными координатами чанка** в массиве размером с мир.
Пока мир фиксирован — это быстро. Для бесконечного мира так нельзя: массив пришлось бы
делать на 30 млн блоков.

## 2. Целевая архитектура

### 2.1 Ключ и состояния чанка

```cpp
using ChunkKey = int64_t; // dim (2 бита) | x (31) | z (31)

enum class ChunkState { Unloaded, Queued, Loading, Loaded, Dirty, Saving };
```

Активный набор:

```cpp
std::unordered_map<ChunkKey, LevelChunk*> m_active;   // только загруженные
std::list<ChunkKey> m_lru;                            // порядок вытеснения
size_t m_budgetChunks;                                // лимит по памяти
```

Инвариант: `m_active.size() <= m_budgetChunks`, всё остальное — на диске.

### 2.2 Загрузка и выгрузка

- Загрузка асинхронная: поток читает регион, распаковывает, кладёт чанк в `m_active`.
- Пока чанк не загружен, `getChunk()` возвращает `emptyChunk` (как сейчас за границей мира).
- Выгрузка: грязный чанк → в очередь сохранения → после записи удаляется из памяти.
- Радиус «обязательных» чанков: `renderDistance + 2` (запас на post-processing соседей).
- Приоритет: сначала чанки рядом с игроком, затем остальные.

### 2.3 Замена прямого индекса

`Level::getBrightness()` сейчас лезет в `chunkSourceCache[idx]` напрямую. Варианты:

- **A (проще):** `getCache()` возвращает `nullptr`, все обращения идут через `getChunk()`.
  Медленнее, но безопасно; дальше оптимизировать.
- **B (быстрее):** thread-local кэш 3×3 чанков вокруг последней точки, сбрасывается при выгрузке.

Начинать с A, потом B по профилю.

### 2.4 Рендер — главный риск

Сейчас `globalIdx` = абсолютная позиция чанка в массиве мира.
Для бесконечности нужно окно вокруг игрока:

- Кольцевой буфер: `idx = (x & 511) * 512 + (z & 511)`, плюс `epoch`/поколение,
  чтобы отличить старые данные при переходе границы окна.
- Или `unordered_map<ChunkKey, ClipChunk*>`, но это дороже в горячем цикле.
- `chunkLists = MemoryTracker::genLists(getGlobalChunkCount()*2)` — сейчас статический
  массив на весь мир. Нужно выделять списки на видимые чанки и переиспользовать.

Без переделки этого места остальное не имеет смысла: рендер просто не увидит чанки за 864.

### 2.5 Генерация

- `RandomLevelSource` уже детерминирован от координат и seed — это хорошо.
- Плохо: `VillageFeature`, `StrongholdFeature`, `NetherBridgeFeature`, `END_LEVEL_MAX_WIDTH`
  используют `XZSize` для раскладки. Нужно заменить на правила, не зависящие от размера мира:
  - деревни/храмы — по сетке регионов с seed;
  - крепости — фиксированное кольцо вокруг спавна;
  - Энд — отдельный маленький мир, его можно оставить как есть.
- Post-processing соседей уже работает через флаги `terrainPopulated` — сохранить,
  но гарантировать, что 8 соседних чанков загружены (отсюда halo +2).

### 2.6 Сохранение

- Регион 32×32 чанка, файл на регион, разреженный.
- Пишем только грязные чанки, бюджет на тик (сейчас `MAX_SAVES`).
- Атомарность: писать во временный файл + переименование, иначе краш = битый мир.
- Легаси-мир 864 при открытии: все чанки считаются сгенерированными,
  граница мира остаётся 864 (режим «старый сейв»), пока игрок не расширит её вручную.

### 2.7 Границы

- Убрать проверки `x < -MAX_LEVEL_SIZE` оставить как страховку (30 млн блоков).
- `LevelData::m_xzSize` — только для легаси-мира, не для новых.
- `PlayerChunkMap`, `LoginPacket` (`writeShort(m_xzSize)`) — проверить, что размер не шлётся
  как обязательный параметр; для бесконечности это поле нужно либо убрать, либо ставить 0.

## 3. Этапы

| Этап | Что | Проверка |
|---|---|---|
| M0 | Собрать PC x64, профилировать, замерить RAM на 864 | билд запускается |
| M1 | Выгрузка чанков без диска (LRU + повторная генерация) | мир 864 работает, RAM падает |
| M2 | Чтение/запись чанков на диск по требованию | сейв/лоад без потерь |
| M3 | Снятие границы, генерация за 864 | можно уйти за край, мир растёт |
| M4 | Рендер: окно вместо абсолютных индексов | нет дыр и out-of-bounds |
| M5 | Фичи мира: структуры, спавн, ад, Энд | новые территории генерятся корректно |
| M6 | Xbox 360 (нужен XDK), бюджет памяти и I/O | 30+ FPS, нет фризов на подгрузке |
| M7 | Мультиплеер, легаси-сейвы, миграция | 2+ игрока, старые миры открываются |

M0–M4 можно сделать и проверить на PC. M6 без XDK невозможен.

## 4. Риски

1. **Рендер** — самая глубокая часть; абсолютная индексация размазана по `LevelRenderer`,
   `Chunk`, `ClipChunk`, SPU-задачам PS3.
2. **Свет на границах** — при выгрузке чанка соседние могут остаться с неверным освещением.
3. **Детерминизм** — старые сейвы не должны «поехать» при новой генерации.
4. **I/O на 360** — HDD медленный; нужен prefetch и ограничение очереди.
5. **Мультиплеер** — `PlayerChunkMap`, `MultiPlayerChunkCache` живут по тем же допущениям.
6. **Память под сейв** — регион-файлы на 360 пишутся через `ConsoleSaveFile`, у него свои лимиты.
